Architecture

总体架构

三通道接入共享同一服务内核；摄取管线异步隔离，避免大文件解析拖垮在线查询；数据层四库各司其职。

Stack

技术选型

环节选型理由
服务框架Python 3.12 + FastAPI + Pydantic v2RAG 生态最全；异步高并发；类型安全

解析主线MinerU + PaddleOCR；unstructured/docling 兜底中文版面/公式/表格解析事实标准

MCP官方 mcp Python SDKstdio（本地）+ streamable HTTP（远程）双 transport

VRAM Budget

GPU 显存预算（关键决策）

8~16GB 单卡上，嵌入、重排、生成三个模型必须精细排布。原则：嵌入必须 GPU 常驻（千万级 chunk 摄取是吞吐关键），reranker 是唯一可降级项（CPU 重排只影响延迟，不影响正确性）。

要点设计
生命周期状态机uploaded → parsed → chunked → embedded → indexed → ready / failed，每阶段落库，可重试、断点续传
幂等与增量文件内容哈希去重；chunk 哈希变化才重新嵌入；网页按 URL 增量 upsert，源站删除则清理
parent-child子块（≈512 token）检索，命中后回填父块（≈2048 token）入生成，兼顾召回精度与上下文完整
代码策略函数/类级切分，chunk 头注入 repo#path#symbol 与 docstring，支持按仓库过滤
表格策略MinerU 转 Markdown 后表头与每行分别建 chunk 并互挂引用，解决「表头丢失」问题
批量嵌入Worker 攒批（128~256）调 TEI，dense + sparse 一次生成、双向量同时写入

  • 混合检索：dense 语义召回 + sparse 关键词召回，RRF 融合（Qdrant Query API 原生，无外部编排）
  • 查询处理：规则型改写默认开启；LLM 改写（多查询、HyDE）作为可选增强，避免每次查询都烧 token
  • 过滤前置：KB / 类型 / 时间等标量过滤先于融合，缩小候选集
  • 生成策略：系统提示强制「仅依据给定上下文 + 逐条引用 [n]」；重排最高分低于阈值 → 明确拒答而非编造
  • 结构化引用：citations 字段随答案返回（chunk id → 来源文件 → 页码/行号；代码库为 repo#path#symbol），供 Agent 二次利用
  • 可选 GraphRAG：LightRAG 模块化接入，实体/关系独立索引，面向多跳问答，默认关闭（Phase 5）
Storage & Capacity

存储与容量规划

Qdrant Collection 设计

  • 命名向量：dense（1024 维 float32）+ sparse（bge-m3 学习稀疏）
  • Payload 最小化：只存 kb_id / doc_id / chunk_id / 类型 / 时间戳 等过滤字段，chunk 正文存 Postgres，检索后按 id 回查，避免 Qdrant 膨胀
  • HNSW：m=16, ef_construct=200；查询 ef=128~256

容量估算（千万级 chunk）

项估算
dense 向量（含 HNSW 开销）1024维 f32 = 4KB × 1000万 ≈ 40GB → 55~60GB
sparse 向量≈ 5~15GB
原始文件（MinIO）2~5TB（视平均文件大小）
元数据 + chunk 正文（Postgres）≈ 30~80GB
内存64GB 舒适（HNSW 常驻 + page cache），32GB 为下限
磁盘NVMe ≥ 2TB 建议

吞吐估算

环节估算
嵌入GPU 批处理 ≈ 500~1500 chunk/s → 1000万 chunk ≈ 2~5 小时（模型侧）
解析MinerU 1~3 s/页（CPU）→ 数十万页需数天，是真正瓶颈，须多 Worker 横向扩展、支持分批导入
在线查询混合检索 + 重排端到端 P95 < 500ms（目标）
生成Qwen3-8B AWQ ≈ 40~80 token/s（满足 Agent 场景）

双 transport：stdio（本机 Claude Code 配置即用）+ streamable HTTP（远程 Agent 接入）；工具描述中嵌入 KB 目录与使用示例，提升 Agent 工具选择准确率。

Deploy & Security

部署与安全

容器资源GPU端口
api（FastAPI）2C/2G否8000
mcp（MCP Server）1C/1G否8100
web（Vue 静态 + nginx）1C/0.5G否8080

vllm（Qwen3）—是9001

tei（reranker）—是（可降 CPU）9003
flower / prometheus / grafana各 1C否5555 / 9090 / 3000
  • 编排：docker-compose 起步，nvidia-container-toolkit 直通 GPU
  • 平台提示：开发可在 Windows（WSL2 GPU 直通）；生产建议 Linux 服务器（GPU 直通、vLLM 兼容性、IO 性能更佳）
  • 扩展路径：API/检索无状态水平扩展；超千万级 chunk 评估 Qdrant 集群或迁 Milvus 分布式；GPU 扩容后按 Profile 升级模型

安全设计

  • 默认绑定 127.0.0.1/内网，对外暴露需显式配置 + TLS
  • API Key 哈希存储，KB 级 ACL（哪个 Key 能读哪些知识库）
  • Redis 令牌桶限流（按 Key + 按 KB 双维度）；上传校验（扩展名 + MIME + 大小上限，可选 ClamAV）
  • 爬虫 SSRF 防护：禁内网/回环地址，域名白名单；日志脱敏：不落 API Key 与敏感内容片段

决策选择备选理由

Risks

风险与缓解

风险影响缓解
Turing SM75 兼容性（vLLM 回归/AWQ 内核） 高生成吞吐跌至 ~1 tok/s 或加载失败版本钉扎 + llama.cpp 备选栈 + Phase 0 Spike 实测矩阵

中文表格/公式检索质量 中命中率低表格专用分块策略、bge-m3 多语言、评估集驱动迭代
检索质量不可度量 高无法迭代Day 1 建评测集，RAGAS 回归进 CI
